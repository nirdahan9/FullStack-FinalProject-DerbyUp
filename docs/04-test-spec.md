## 1. אסטרטגיית הבדיקות

### 1.1 מה בודקים ומה לא

ההנחיות קובעות: *"לא חובה לבדוק כל שורת קוד, אבל חובה לבדוק את התהליכים המרכזיים."*

| נבדק בקפדנות | נבדק בסיסית | לא נבדק |
|---|---|---|
| חישוב הניקוד מהיחס | קומפוננטות UI מרכזיות | קומפוננטות shadcn/ui |
| יישוב וחישוב דירוג | טפסים | סגנון ופריסה |
| הרשאות ובידוד נתונים | ניווט | לוגים |
| ולידציות קלט | | קוד ספריות צד ג' |
| התהליך העסקי מקצה לקצה | | |

### 1.2 פירמידת הבדיקות

```
        ╱╲          E2E — Playwright
       ╱  ╲         מעט, איטיות, מכסות את המסע המלא
      ╱────╲
     ╱      ╲       אינטגרציה — Vitest מול Supabase
    ╱        ╲      RLS, הרשאות, ודירוג מחושב
   ╱──────────╲
  ╱            ╲    יחידה — Vitest
 ╱______________╲   רבות, מהירות, על lib/domain/
```

**הרוב המכריע של הלוגיקה נבדק ביחידה**, כי `lib/domain/` תוכננה כפונקציות טהורות בלי I/O.

### 1.3 כלים

| כלי | שכבה |
|---|---|
| **Vitest** | יחידה + אינטגרציה |
| **React Testing Library** | קומפוננטות |
| **Playwright** | E2E בדפדפן אמיתי |
| בדיקות ידניות מתועדות | מה שלא כדאי לאוטמט (§9) |

### 8.2 E2E — המסע המרכזי (Playwright)

> תרחיש אחד שלם שעובר את כל המוצר. אם הוא עובר — הלולאה המרכזית עובדת.

```
1.  הרשמה של משתמש חדש
2.  אימות: 0 נקודות מוצגות
3.  יצירת ליגה + בחירת טורניר + הגדרת פרסים → קוד הזמנה מוצג
4.  התנתקות
5.  הרשמת משתמש שני
6.  הצטרפות עם הקוד
7.  אימות: הליגה מופיעה בדשבורד עם הטורניר והפרסים
8.  מעבר למשחקים → אימות: רק משחקי הטורניר מוצגים
9.  בחירת משחק → ניחוש בלחיצה אחת
10. אימות: הניחוש מופיע כ"ממתין" עם היחס שהוקפא
11. הרצת יישוב (seed תוצאה + הפעלת cron)
12. אימות: הסטטוס התעדכן ל"צדקת"
13. אימות: הנקודות שהתקבלו = היחס
14. אימות: טבלת הדירוג מציגה את שני המשתמשים בסדר הנכון
```

### 8.3 E2E — תרחישים נוספים

|---|---|
