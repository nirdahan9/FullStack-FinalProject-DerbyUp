## 1. מה יקרה עם עשרות עד מאות משתמשים

### 1.1 פרופיל העומס הצפוי

DerbyUp הוא מוצר B2B פנים-ארגוני. זה משנה מהותית את תמונת הסקייל:

| מאפיין | ערך צפוי |
|---|---|
| ארגון טיפוסי | 100–500 עובדים |
| שיעור השתתפות | 20–40% |
| משתמשים פעילים בליגה | 30–200 |
| **תבנית העומס** | **פרצי שיא**, לא זרימה אחידה |

### 1.2 הפרץ — התובנה המרכזית

השימוש **אינו מפוזר**. הוא מתרכז בשני חלונות:

| חלון | מה קורה | עומס |
|---|---|---|
| **שעה לפני מחזור** | כולם מנחשים | 🔴 שיא כתיבה |
| **מיד אחרי יישוב** | כולם בודקים את הטבלה | 🔴 שיא קריאה |
| שאר הזמן | טפטוף | 🟢 אפסי |

**המשמעות:** ליגה של 200 עובדים יכולה לייצר 200 כתיבות ב-10 דקות ואז שקט מוחלט. התכנון
מתייחס לשיא, לא לממוצע.

### 1.3 הערכה כמותית

| תרחיש | משתמשים | פעולות בשיא | הערכה |
|---|---|---|---|
| ליגה בודדת | 50 | ~150 ניחושים/שעה | ✅ זניח |
| ארגון בינוני | 200 | ~600 ניחושים/שעה | ✅ נוח |
| כמה ארגונים | 1,000 | ~3,000 ניחושים/שעה | ✅ בגבולות ה-free tier |
| 10,000 | 10,000 | ~30,000/שעה | ⚠️ דורש שדרוג — §8 |

> ~3,000 כתיבות בשעה הן פחות מכתיבה בשנייה בממוצע. Postgres מטפל בזה בלי מאמץ.
> **הצוואר האמיתי אינו ה-DB אלא ספק הנתונים החיצוני** — §6.

## 2. שאילתות שעלולות להיות כבדות

### 2.1 המועמדות

| # | שאילתה | למה כבדה | מענה בתכנון |
|---|---|---|---|
| 1 | **טבלת דירוג** | ⚠️ **אגרגציה מחושבת** לכל חבר | אינדקס חלקי + pagination + מסלול ל-materialized view |
| 2 | **היסטוריית ניחושים** | גדלה ללא הגבלה | אינדקס + pagination |
| 3 | **משחקים קרובים** | סינון על תחרות וטווח זמן | אינדקס משולב |
| 4 | **יישוב** | עדכון המוני | עיבוד באצווה |
| 5 | **autocomplete שחקנים** | חיפוש תת-מחרוזת | GIN trigram |
| 6 | **התראות שלא נקראו** | סינון על עמודה דלילה | אינדקס חלקי |

### 2.2 טבלת דירוג — השאילתה היקרה ביותר במערכת

זו הנקודה הכבדה ביותר, **כתוצאה ישירה מהחלטה ארכיטקטונית**: לליגה אין עמודת ניקוד
מאוחסנת, והדירוג **מחושב בזמן קריאה** מסכום הנקודות של כל חבר על משחקי התחרות של הליגה,
מרגע הצטרפותו (ראה [03-technical-design.md](03-technical-design.md) §2.2).

```sql
select lm.user_id, p.display_name,
       coalesce(pred.pts,0) + coalesce(puz.pts,0) as league_points
from league_members lm
join profiles p on p.id = lm.user_id
left join lateral (
  select sum(pr.points_earned) as pts
  from predictions pr
  join questions q on q.id = pr.question_id
  join games    g on g.id = q.game_id
  where pr.user_id = lm.user_id and pr.status = 'correct'
    and g.competition_id = $1 and pr.predicted_at >= lm.joined_at
) pred on true
left join lateral (...) puz on true
where lm.league_id = $2
order by league_points desc;
```

**העלות:** subquery מצרפי לכל חבר → `O(members × predictions_per_member)`.
לליגה של 200 חברים עם 100 ניחושים לכל אחד — כ-20,000 שורות. **זניח** ל-Postgres.

**מה מרסן את זה:**

| מנגנון | תרומה |
|---|---|
| `idx_pred_user_status` — אינדקס **חלקי** על `status='correct'` | סורק רק ניחושים נכונים, כשליש מהנפח |
| `idx_games_comp_kickoff` | סינון התחרות בלי סריקת `games` |
| הגבלת החלון ל-7 ימים קדימה | `games` נשארת קטנה |

**המחיר של ההחלטה, בכנות:** עמודה מאוחסנת הייתה נותנת קריאה של `O(log n)`. בחרנו
בחישוב כדי שלא תהיה אפשרות לסטייה בין הניקוד המוצג לנתונים. בהיקף הנוכחי המחיר זניח,
ומסלול השדרוג ברור — `MATERIALIZED VIEW` שמתרענן ביישוב (§9.1).

### 2.2.1 מה **לא** כבד יותר במודל הזה

מודל "היחס הוא הניקוד" ביטל שאילתות שהיו קיימות בתכנון הקודם:

| מה נעלם | למה |
|---|---|
| חישוב יתרה מספר תנועות | אין ספר תנועות |
| בדיקת יתרה בכל ניחוש | אין מה לבדוק |
| עדכון `points_in_league` ביישוב | הדירוג מחושב |
| טרנזקציה מרובת-טבלאות בהנחת ניחוש | `INSERT` בודד לטבלה אחת |

**הנחת ניחוש הפכה מטרנזקציה של שלוש טבלאות ל-`INSERT` יחיד** — שיפור משמעותי דווקא
בחלון שבו העומס הכי גבוה (הפרץ שלפני המחזור).

### 2.3 היישוב — הסכנה האמיתית

הסכנה כאן היא **N+1**: לולאה שמריצה שאילתה לכל ניחוש.

```
❌ אנטי-דפוס:                            ✅ התכנון שלנו:
for (const p of predictions) {          1. שליפת כל הניחושים הממתינים במכה אחת
   await db.query(...)   // N שאילתות      2. חישוב בזיכרון ב-lib/domain/
}                                        3. עדכון באצווה בטרנזקציה אחת
```

100 ניחושים → **3 שאילתות** במקום 100.

## 3. אינדקסים

**כן, בהחלט נדרשים.** בלעדיהם כל שאילתה היא סריקה מלאה.

| אינדקס | סוג | השאילתה | הרווח |
|---|---|---|---|
| `idx_pred_user_status` | **חלקי** (`status='correct'`) | טבלת דירוג | סורק רק ניחושים נכונים |
| `idx_pred_user_time` | B-tree משולב | היסטוריה | סריקה ממוקדת |
| `idx_pred_question_status` | B-tree משולב | יישוב | איתור מהיר של הממתינים |
| `idx_games_comp_kickoff` | B-tree משולב | משחקי התחרות | סינון יעיל בדירוג |
| `idx_games_status_kickoff` | B-tree משולב | משחקים קרובים | סינון יעיל |
| `idx_notif_user_unread` | **חלקי** | התראות | אינדקס קטן — רק לא-נקראות |
| `idx_players_trgm` | **GIN trigram** | autocomplete | חיפוש `%text%` יעיל |

### 3.1 שלוש החלטות אינדוקס

**אינדקס משולב וסדרו.** ב-`(competition_id, kickoff_at)` הסדר קריטי: קודם השוויון
(`competition_id`), אחר כך הטווח. הפוך — האינדקס חסר תועלת לשאילתה הזו.

**אינדקס חלקי — פעמיים.** `where status = 'correct'` על `predictions` ו-`where read_at is null`
על `notifications`. שניהם מכילים **רק** את השורות שנשאלות בפועל, ולכן נשארים קטנים
גם כשהטבלה גדלה. באינדקס הראשון זה מכפיל את התועלת: ניחושים שגויים אף פעם לא נספרים
בדירוג, ולכן אין סיבה שיהיו באינדקס.

**למה לא לאנדקס הכל.** כל אינדקס מאט כתיבות וצורך אחסון. אינדקסנו רק את מה שנגזר משאילתה
אמיתית שזיהינו.

## 5. Pagination

**כן, בכל רשימה שיכולה לגדול.**

```sql
select ... from bets where user_id = $1
order by placed_at desc limit 20 offset $2;
```

| רשימה | גודל עמוד |
|---|---|
| היסטוריית ניחושים | 20 |
| טבלת דירוג | 20 |
| משחקים | 20 |
| התראות | 20 |

### 5.1 מגבלה ידועה: `OFFSET`

`OFFSET` דורש מה-DB לדלג על N שורות פיזית. בעמוד 500 זה מתחיל להיות יקר.

**למה זה מקובל כאן:** אף רשימה במוצר לא צפויה להגיע לעומקים כאלה — ליגה של 200 חברים היא
10 עמודים. **מה נעשה אם כן:** מעבר ל-**keyset pagination** (`where placed_at < $cursor`),
שעלותו קבועה ולא תלויה בעומק.

## 6. הצוואר האמיתי: מכסת API-Football

> זו המגבלה המשמעותית ביותר במוצר — ולא ה-DB.

**ה-tier החינמי מוגבל ל-100 קריאות ביום.** אנחנו מושכים 7 תחרויות.

### 6.1 חישוב תמים — לא עובד

```
7 תחרויות × (fixtures + odds) × 24 הרצות ביום = 336 קריאות  ❌  חריגה של פי 3.4
```

### 6.2 התכנון בפועל

| החלטה | חיסכון |
|---|---|
| `sync-fixtures` **פעם ביום**, לא כל שעה | ×24 → ×1 |
| משיכת חלון של 7 ימים בקריאה אחת | קריאה אחת לתחרות |
| **odds רק למשחקים בליגות פעילות** | לרוב 1–2 תחרויות בפועל |
| התוצאות נשמרות ב-DB | אפס קריאות בזמן צפייה |
| `settle` קורא רק למשחקים שהסתיימו | קריאות בודדות בשעה |

```
7 (fixtures) + ~7 (odds) + ~10 (settle) ≈ 24 קריאות ביום  ✅  בתוך המכסה
```

### 6.3 עקרון

**המשתמשים לעולם אינם מפעילים קריאה ל-API החיצוני.** כל קריאה מגיעה מ-cron מתוזמן. לכן
צריכת ה-API **אינה תלויה במספר המשתמשים** — מיליון משתמשים יצרכו בדיוק אותן 24 קריאות.

## 7. הפרדה בין צד לקוח לצד שרת

### 7.1 החלוקה

| רץ בשרת | רץ בלקוח |
|---|---|
| שליפת נתונים | אינטראקציה בטפסים |
| **כל הלוגיקה העסקית** | ולידציה ויזואלית |
| **כל הולידציות המחייבות** | מצב UI מקומי |
| **כל בדיקות ההרשאות** | החלפת ערכת נושא |
| מפתחות API | |

### 7.2 העיקרון

**הלקוח אינו מהימן.** כל מה שרץ בדפדפן ניתן לשינוי דרך DevTools. לכן:

- ולידציית לקוח = **נוחות**; ולידציית שרת = **אמת**
- כפתור מנוטרל אינו הגנה — הבדיקה חוזרת ב-Server Action
- סודות לעולם לא ב-`NEXT_PUBLIC_*`

### 7.3 `'use client'` במשורה

ברירת המחדל היא Server Component. `'use client'` רק כשצריך state או event handlers, וגם אז
מדחיקים אותו **לעלים של עץ הקומפוננטות** — כך רק החלק האינטראקטיבי נשלח כ-JS.

## 9. שיפורים לגרסה עתידית

### 9.1 קצר טווח — עד ~1,000 משתמשים

| שיפור | מה פותר |
|---|---|
| **Keyset pagination** | מגבלה 1 |
| **עיבוד היישוב באצוות** | מגבלה 2, 7 |
| **Rate limiting** על Actions | מגבלה 10 |
| **Materialized view** לטבלת הדירוג | מגבלה 2א — **השדרוג החשוב ביותר**; מתרענן ביישוב |
| **התאמה תקופתית** של `total_points` מול הניחושים | מגבלה 8 |

### 9.2 טווח בינוני — עד ~10,000

| שיפור | מה פותר |
|---|---|
| **Supabase Pro** + connection pooling | מגבלה 6 |
| **Redis** למטמון טבלאות דירוג | מגבלה 3 |
| **Supabase Realtime** לטבלה חיה | מגבלה 5 |
| **תור עבודה** ליישוב במקום cron | מגבלה 2, 7 |
| **API-Football בתשלום** | מגבלה 4 |
| **CDN לתמונות** | מוריד עומס |

### 9.3 טווח ארוך — מעל 10,000

| שיפור | מה פותר |
|---|---|
| **פיצול (partitioning)** של `bets` לפי תאריך | טבלה שגדלה ללא הגבלה |
| **Read replicas** | הפרדת קריאה מכתיבה |
| **ארכוב** עונות ישנות | שמירה על טבלאות חמות קטנות |
| **פריסה רב-אזורית** | לטיין לארגונים גלובליים |

### 9.4 סדר העדיפויות

אם היה עוד זמן, הייתי מבצע לפי הסדר הזה:

1. **Materialized view לדירוג** — השאילתה היקרה ביותר, והיחידה שגדלה ריבועית
2. **Rate limiting** — הפער הבולט ביותר באבטחה
3. **עיבוד היישוב באצוות** — הצוואר הבא שייפגש בפועל
4. **Keyset pagination** — שינוי קטן, מבטל תקרה
