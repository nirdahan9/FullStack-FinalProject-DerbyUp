### 2.1 למה שכבת דומיין נפרדת

`lib/domain/` מכילה **פונקציות טהורות בלבד** — מקבלות נתונים ומחזירות נתונים, בלי גישה ל-DB
ובלי רשת. זו החלטה מכוונת:

- **נבדקת בקלות** — בדיקות יחידה בלי mock, בלי DB, בלי רשת
- **הלוגיקה העסקית במקום אחד** — לא מפוזרת בין קומפוננטות
- **ניתנת לשימוש חוזר** — אותה פונקציה משמשת ב-Server Action וב-cron

> זו התשובה לדרישת ההנחיות "תיאור הלוגיקה העסקית המרכזית" ולדרישת הבדיקות המשמעותיות.

## 3. האם משתמשים במסד נתונים

**כן — PostgreSQL מנוהל ב-Supabase.** הנימוקים:

| שיקול | למה Postgres רלציוני |
|---|---|
| **קשרים** | משתמש ↔ ליגה ↔ ניחוש ↔ משחק — גרף רלציוני מובהק |
| **שלמות נתונים** | מפתחות זרים מונעים ניחוש למשחק שלא קיים |
| **טרנזקציות** | היישוב מעדכן ניחושים, מטמון ניקוד והתראות יחד. חייב אטומי |
| **צבירה** | טבלת דירוג היא `SUM`/`ORDER BY` — נקודת החוזק של SQL |
| **RLS** | Postgres אוכף הרשאות **בשכבת ה-DB**, לא רק באפליקציה |

        │         │ questions │                 └─────┬────────┘
        │         └──────┬────┘                       │ 1:N

### 4.1 הטבלאות

| # | טבלה | תיאור |
|---|---|---|
| 1 | `profiles` | פרופיל משתמש; `id` = FK ל-`auth.users` |
| 2 | `competitions` | 7 התחרויות הנתמכות |
| 3 | `games` | משחקים ותוצאות |
| 4 | `questions` | 3 שאלות למשחק + היחסים |
| 5 | `predictions` | ניחוש של משתמש (גלובלי) |
| 6 | `leagues` | ליגה ארגונית — קשורה לתחרות אחת |
| 7 | `league_members` | חברות בלבד — **בלי עמודת ניקוד** |
| 8 | `notifications` | התראות פר-משתמש |
| 9 | `user_achievements` | הישגים שהושגו |
| 10 | `daily_puzzles` | אתגר יומי |
| 11 | `puzzle_attempts` | ניסיונות באתגר |
| 12 | `bridge_players` | מאגר שחקנים ל-autocomplete |

> המבנה המלא עם טיפוסים ואילוצים נמצא ב-[03-technical-design.md](03-technical-design.md).

### 4.2 החלטה: אין ספר תנועות ואין ניקוד מאוחסן בליגה

**מודל הניקוד:** ניחוש נכון מזכה ב**יחס** כנקודות (יחס 7.15 → 7.15 נקודות); ניחוש שגוי
מזכה באפס. אין stake, אין יתרה, אין הפסד.

מכאן נגזרות שתי החלטות מבניות:

**1. אין `point_transactions`.** ספר תנועות נחוץ כשיש הוצאה והכנסה ויתרה שעלולה להשתבש.
כאן **נקודות רק נצברות ולעולם לא נגרעות**, וכל צבירה כבר רשומה במקורה
(`predictions.points_earned`, `puzzle_attempts.points_earned`). ספר נפרד היה כפילות.

**2. אין `points_in_league`.** הדירוג **מחושב בזמן קריאה** מסכום הנקודות של החבר על משחקי
התחרות של הליגה, מרגע הצטרפותו. עמודה מאוחסנת עלולה לסטות מהאמת; כאן יש מקור אמת יחיד.

| יתרון | הסבר |
|---|---|
| אין סטייה אפשרית | הדירוג נגזר תמיד מהנתונים עצמם |
| פחות טבלאות ופחות עמודות | פחות קוד, פחות מצבי קצה |
| אין race conditions | אין ערך משותף שמעדכנים במקביל |

`profiles.total_points` נשמרת כ**מטמון** לקריאה מהירה בפרופיל, ולא כמקור אמת.

## 6. Server Actions ו-Route Handlers

### 6.1 החלטה: Server Actions במקום REST API

| שיקול | Server Actions | REST API |
|---|---|---|
| Type safety | מקצה לקצה, בלי טיפוסים ידניים | דורש הגדרה כפולה |
| Boilerplate | פונקציה אחת | route + fetch + טיפוסים |
| אבטחה | רץ בשרת בלבד; אי אפשר לעקוף ולידציה | חשוף כ-endpoint ציבורי |
| מתאים ל | פעולות מתוך ה-UI | לקוחות חיצוניים |

מכיוון שאין לנו לקוחות חיצוניים, Server Actions הן הבחירה הנכונה. **REST נשמר רק ל-cron**,
שהוא באמת קורא חיצוני.

### 6.2 Server Actions

| Action | קלט | פעולה | הרשאה |
|---|---|---|---|
| `signUp` / `signIn` / `signOut` | credentials | ניהול session | ציבורי |
| `createLeague` | שם, תיאור, תחרות | יצירת ליגה + קוד | מחובר |
| `joinLeague` | קוד | הוספת חבר | מחובר |
| `makePrediction` | שאלה, בחירה | ולידציה → הקפאת יחס → ניחוש | מחובר |
| `cancelPrediction` | מזהה ניחוש | ביטול עד 10 דק' לפני פתיחה | בעל הניחוש |
| `updatePrizes` | פרסים לפי מקום | עדכון פרסי הליגה | אדמין ליגה |
| `submitPuzzleAnswer` | שם שחקן | בדיקה → זיכוי | מחובר |
| `updateProfile` | שם, אווטאר | עדכון | בעל הפרופיל |
| `selectLeagueGames` | מזהי משחקים | קביעת משחקי הליגה | אדמין ליגה |
| `setFeaturedGame` | משחק, בונוס | משחק שבוע | אדמין ליגה |
| `settleGameManually` | משחק, תוצאה | יישוב ידני | אדמין ליגה |
| `markNotificationRead` | מזהה | סימון כנקרא | בעל ההתראה |

### 6.3 Route Handlers

| מסלול | תדירות | פעולה |
|---|---|---|
| `/api/cron/sync-fixtures` | יומי | משיכת משחקים + יחסים; בניית שאלות |
| `/api/cron/settle` | כל שעה | יישוב משחקים שהסתיימו + הישגים + התראות |
| `/api/cron/publish-puzzle` | יומי | פרסום אתגר היום |

שלושתם מוגנים ב-`CRON_SECRET` ומוגדרים ב-`vercel.json`.

## 7. זרימת מידע

### 7.1 קריאה — טעינת טבלת דירוג

```
דפדפן → בקשה ל-/leagues/[id]
   │
   ▼
Server Component (רץ בשרת)
   │  קורא ל-Supabase עם ה-session של המשתמש
   ▼
Postgres — RLS בודק: המשתמש חבר בליגה?
   │  כן → מחשב את הדירוג באגרגציה · לא → מחזיר ריק
   ▼
HTML מרונדר בשרת ← נשלח לדפדפן
```

> הדירוג **מחושב** ולא נשלף מעמודה — סכום הנקודות של כל חבר על משחקי התחרות של הליגה,
> מרגע הצטרפותו.

> **הנקודה החשובה:** הנתונים לא עוברים דרך API ציבורי ולא נחשפים ללקוח. הדפדפן מקבל HTML מוכן.

### 7.2 כתיבה — הנחת ניחוש

```
לקוח: לוחץ על אפשרות
   │
   ▼
Server Action makePrediction()
   │
   ├─ 1. אימות session — מחובר?
   ├─ 2. ולידציית Zod — questionId, outcome
   ├─ 3. שליפת השאלה והמשחק
   ├─ 4. כללי דומיין: המשחק טרם התחיל? אין ניחוש קיים?
   │                  המשתמש חבר בליגה של התחרות?
   ├─ 5. הקפאת היחס הנוכחי + בונוס משחק שבוע
   │
   ▼  INSERT predictions   ← פעולה אחת, טבלה אחת
   │
   ▼
revalidatePath() → ה-UI מתרענן
```

> **פשטות המודל בולטת כאן:** אין טרנזקציה מרובת-טבלאות, אין עדכון יתרה, אין חיוב.

### 7.3 עיבוד רקע — יישוב

```
Vercel Cron (כל שעה) → /api/cron/settle
   │  אימות CRON_SECRET
   ▼
משיכת תוצאות מ-API-Football
   ▼
עדכון games; קביעת התשובה הנכונה לכל שאלה
   ▼
לכל ניחוש ממתין: settlePrediction() ב-lib/domain
   ▼  טרנזקציה:
   ├─ UPDATE predictions (status + points_earned = היחס המוקפא)
   ├─ UPDATE profiles.total_points (מטמון)
   ├─ INSERT notifications
   └─ בדיקת הישגים

   ⚠️ אין עדכון של דירוג הליגה — הוא מחושב בזמן קריאה
```

## 8. משתמשים והרשאות

### 8.1 שלוש רמות

| רמה | מי | יכולות |
|---|---|---|
| **אורח** | לא מחובר | דף נחיתה, הרשמה, התחברות |
| **משתמש רשום** | עובד | ניחוש, הצטרפות, אתגר, פרופיל, הליגות שלו |
| **אדמין ליגה** | יוצר הליגה | כל הנ"ל + ניהול הליגה שיצר |

### 8.2 אדמין ליגה — החלטה

`leagues.creator_id` הוא האדמין. **קבוע, לא ניתן להעברה.** ההחלטה מפשטת:

- אין טבלת תפקידים נפרדת
- אין flows של הענקה/שלילה
- בדיקת ההרשאה היא `leagues.creator_id = auth.uid()` — פשוט לאכוף ב-RLS

### 8.3 שתי שכבות אכיפה

| שכבה | איפה | תפקיד |
|---|---|---|
| **אפליקציה** | middleware + Server Actions | חוויית משתמש — הפניה, הודעות שגיאה |
| **מסד נתונים** | RLS | **קו ההגנה האמיתי** |

> אכיפה כפולה בכוונה: גם אם באג באפליקציה, RLS עוצר את הדליפה. פירוט ב-[06-security.md](06-security.md).

## 9. ספריות ושירותים חיצוניים

### 9.1 שירותים

| שירות | תפקיד | למה נבחר |
|---|---|---|
| **Vercel** | אירוח | יצרנית Next.js; Cron מובנה; preview לכל commit |
| **Supabase** | DB + Auth | Postgres מנוהל **עם RLS** — אכיפת הרשאות ברמת ה-DB |
| **API-Football** | נתוני כדורגל | **ספק יחיד** למשחקים, תוצאות **ויחסים**. היחסים הם הניקוד — ולכן קריטיים |

### 9.2 החלטה: ספק נתונים אחד

הפרויקט המקורי השתמש בשלושה ספקים (ESPN, The Odds API, API-Football). בבדיקה עלה
ש-API-Football מספק דרך `/odds` **בדיוק** את שלושת השווקים שבחרנו. לכן:

**ספק אחד = פחות תלויות · סוד אחד לנהל · פחות קוד התאמה בין מקורות · פחות מצבי כשל.**

### 9.3 ספריות

| ספרייה | תפקיד | נימוק |
|---|---|---|
| **Next.js 15** | framework | נדרש בהנחיות; App Router ו-Server Actions |
| **TypeScript** | שפה | נדרש בהנחיות; טיפוסים נגזרים מסכימת ה-DB |
| **Tailwind CSS** | עיצוב | RTL ומצב כהה דרך טוקנים |
| **shadcn/ui** | קומפוננטות | קוד בפרויקט, לא תלות — ניתן להתאמה מלאה |
| **Zod** | ולידציה | סכימה אחת ל-client ול-server; מסיק טיפוסים |
| **@supabase/ssr** | session | ניהול cookies נכון ב-App Router |
| **date-fns** | תאריכים | קל מ-moment, tree-shakeable |
| **lucide-react** | אייקונים | תואם shadcn/ui |
| **Vitest** | בדיקות יחידה | מהיר; משתף config עם Vite |
| **React Testing Library** | בדיקות קומפוננטות | בדיקה מנקודת מבט המשתמש |
| **Playwright** | E2E | דפדפן אמיתי; מומלץ בהנחיות |

### 9.4 מה לא נכלל ולמה

| לא נכלל | למה |
|---|---|
| Redux / Zustand | Server Components מייתרים את רוב ה-state הגלובלי |
| Prisma / Drizzle | Supabase מייצר טיפוסים מהסכימה; ORM נוסף = שכבה מיותרת |
| React Query | הנתונים נטענים בשרת; אין צורך במטמון בלקוח |
| Redis | אין עדיין עומס שמצדיק מטמון נוסף |
| The Odds API | API-Football מכסה את הצורך |

## 11. סביבות ומשתני סביבה

| משתנה | תפקיד | חשוף ללקוח? |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | כתובת הפרויקט | כן |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | מפתח ציבורי (כפוף ל-RLS) | כן |
| `SUPABASE_SERVICE_ROLE_KEY` | **עוקף RLS** — cron בלבד | **לא** |
| `FOOTBALL_API_KEY` | API-Football | **לא** |
| `CRON_SECRET` | אימות cron | **לא** |

> מפתח ה-service role עוקף RLS ולכן משמש **אך ורק** ב-Route Handlers של cron, לעולם לא
> ב-Server Component או Action שרץ בהקשר משתמש.
